L412: # torch.export IR Specificationcite235†#
L413: 
L414: Created On: Oct 05, 2023 | Last Updated On: Dec 09, 2025
L415: 
L416: Export IR is an intermediate representation (IR) for compilers, which bears similarities to cite236†MLIR†mlir.llvm.org and TorchScript. It is specifically designed to express the semantics of PyTorch programs. Export IR primarily represents computation in a streamlined list of operations, with limited support for dynamism such as control flows.
L417: To create an Export IR graph, a frontend can be used that soundly captures a PyTorch program via a trace-specializing mechanism. The resulting Export IR can then be optimized and executed by a backend. This can be done today through cite237†`torch.export.export()` .
L418: 
L419: The key concepts that will be covered in this document include:
L420: 
L421:   * ExportedProgram: the data structure containing the Export IR program
L422: 
L423:   * Graph: which consists of a list of nodes.
L424:   * Nodes: which represents operations, control flow, and metadata stored on this node.
L425: 
L426:   * Values are produced and consumed by nodes.
L427: 
L428:   * Types are associated with values and nodes.
L429: 
L430:   * The size and memory layout of values are also defined.
L431: ## Assumptionscite238†#
L432: 
L433: This doc assumes that the audience is sufficiently familiar with PyTorch, specifically with cite239†`torch.fx` and its related toolings. Thus it will stop describing contents present in cite239†`torch.fx` documentation and paper.
L434: ## What is Export IRcite240†#
L435: 
L436: Export IR is a graph-based intermediate representation IR of PyTorch programs. Export IR is realized on top of cite241†`torch.fx.Graph` . In other words, all Export IR graphs are also valid FX graphs, and if interpreted using standard FX semantics, Export IR can be interpreted soundly. One implication is that an exported graph can be converted to a valid Python program via standard FX codegen.
L437: This documentation will primarily focus on highlighting areas where Export IR differs from FX in terms of its strictness, while skipping parts where it shares similarities with FX.
L438: ## ExportedProgramcite242†#
L439: 
L440: The top-level Export IR construct is an cite243†`torch.export.ExportedProgram` class. It bundles the computational graph of a PyTorch model (which is usually a cite244†`torch.nn.Module` ) with the parameters or weights that this model consumes.
L441: 
L442: Some notable attributes of the cite243†`torch.export.ExportedProgram` class are:
L443:   * `graph_module` (cite245†`torch.fx.GraphModule` ): Data structure containing the flattened computational graph of the PyTorch model. The graph can be directly accessed through `ExportedProgram.graph`.
L444:   * `graph_signature` (`torch.export.ExportGraphSignature`): The graph signature, which specifies the parameters and buffer names used and mutated within the graph. Instead of storing parameters and buffers as attributes of the graph, they are lifted as inputs to the graph. The graph_signature is utilized to keep track of additional information on these parameters and buffers.
L445: 
L446:   * `state_dict` (`Dict[str, Union[torch.Tensor, torch.nn.Parameter]]`): Data structure containing the parameters and buffers.
L447:   * `range_constraints` (`Dict[sympy.Symbol, RangeConstraint]`): For programs that are exported with data dependent behavior, the metadata on each node will contain symbolic shapes (which look like `s0`, `i0`). This attribute maps the symbolic shapes to their lower/upper ranges.
L448: ## Graphcite246†#
L449: 
L450: An Export IR Graph is a PyTorch program represented in the form of a DAG (directed acyclic graph). Each node in this graph represents a particular computation or operation, and edges of this graph consist of references between nodes.
L451: 
L452: We can view Graph having this schema:
L453: 
L454:     class Graph:
L455:       nodes: List[Node]
L456: 
L457: 
L458: In practice, Export IR’s graph is realized as cite241†`torch.fx.Graph` Python class.
L459: An Export IR graph contains the following nodes (Nodes will be described in more details in the next section):
L460: 
L461:   * 0 or more nodes of op type `placeholder`
L462: 
L463:   * 0 or more nodes of op type `call_function`
L464: 
L465:   * exactly 1 node of op type `output`
L466: 
L467: Collorary: The smallest valid Graph will be of one node. i.e. nodes is never empty.
L468: Definition: The set of `placeholder` nodes of a Graph represents the inputs of the Graph of GraphModule. The `output` node of a Graph represents the outputs of the Graph of GraphModule.
L469: Example:
L470: 
L471:     import torch
L472:     from torch import nn
L473: 
L474:     class MyModule(nn.Module):
L475: 
L476:         def forward(self, x, y):
L477:           return x + y
L478: 
L479:     example_args = (torch.randn(1), torch.randn(1))
L480:     mod = torch.export.export(MyModule(), example_args)
L481:     print(mod.graph)
L482: 
L483: 
L484:     graph():
L485:       %x : [num_users=1] = placeholder[target=x]
L486:       %y : [num_users=1] = placeholder[target=y]
L487:       %add : [num_users=1] = call_function[target=torch.ops.aten.add.Tensor](args = (%x, %y), kwargs = {})
L488:       return (add,)
L489: The above is the textual representation of a Graph, with each line being a node.
L490: ## Nodecite247†#
L491: 
L492: A Node represents a particular computation or operation and is represented in Python using the cite248†`torch.fx.Node` class. Edges between nodes are represented as direct references to other nodes via the `args` property of the Node class. Using the same FX machinery, we can represent the following operations that a computational graph typically needs, such as operator calls, placeholders (aka inputs), conditionals, and loops.
L493: The Node has the following schema:
L494: 
L495:     class Node:
L496:       name: str # name of node
L497:       op_name: str  # type of operation
L498: 
L499:       # interpretation of the fields below depends on op_name
L500:       target: [str|Callable]
L501:       args: List[object]
L502:       kwargs: Dict[str, object]
L503:       meta: Dict[str, object]
L504: 
L505: 
L506: FX Text Format
L507: As in the example above, notice that each line has this format:
L508: 
L509:     %<name>:[...] = <op_name>[target=<target>](args = (%arg1, %arg2, arg3, arg4, …)), kwargs = {"keyword": arg5})
L510: 
L511: 
L512: This format captures everything present in the Node class, with the exception of `meta`, in a compact format.
L513: 
L514: Concretely:
L515: 
L516:   * <name> is the name of the node as it would appear in `node.name`.
L517:   * <op_name> is the `node.op` field, which must be one of these: `<call_function>`, `<placeholder>`, `<get_attr>`, or `<output>`.
L518: 
L519:   * <target> is the target of the node as `node.target`. The meaning of this field depends on `op_name`.
L520: 
L521:   * args1, … args 4… are what is listed in the `node.args` tuple. If a value in the list is an cite248†`torch.fx.Node` , then it will be especially indicated with a leading %.
L522: For example, a call to the add operator would appear as:
L523: 
L524:     %add1 = call_function[target = torch.op.aten.add.Tensor](args = (%x, %y), kwargs = {})
L525: 
L526: 
L527: Where `%x`, `%y` are two other Nodes that have names x and y. Worth noting that the string `torch.op.aten.add.Tensor` represents the callable object that is actually stored in the target field, not merely its string name.
L528: 
L529: The final line of this text format is:
L530: 
L531:     return [add]
L532: which is a Node with `op_name = output`, indicating that we are returning this one element.
L533: ### call_functioncite249†#
L534: 
L535: A `call_function` node represents a call to an operator.
L536: 
L537: Definitions
L538: 
L539:   * Functional: We say a callable is “functional” if it satisfies all the following requirements:
L540: 
L541:     * Non-mutating: The operator does not mutate the value of its input (for tensors, this includes both metadata and data).
L542: 
L543:     * No side effects: The operator does not mutate states that are visible from outside, like changing values of module parameters.
L544:   * Operator: is a functional callable with a predefined schema. Examples of such operators include functional ATen operators.
L545: 
L546: Representation in FX
L547: 
L548:     %name = call_function[target = operator](args = (%x, %y, …), kwargs = {})
L549: 
L550: 
L551: Differences from vanilla FX call_function
L552: 
L553:   1. In FX graph, a call_function can refer to any callable, in Export IR, we restrict it to only a select subset of ATen operators, custom operators, and control flow operators.
L554:   2. In Export IR, constant arguments will be embedded within the graph.
L555: 
L556:   3. In FX graph, a get_attr node can represent reading any attribute stored in the graph module. However, in Export IR this is restricted to reading only submodules as all parameters/buffers will be passed in as inputs to the graph module.
L557: #### Metadatacite250†#
L558: 
L559: `Node.meta` is a dict attached to every FX node. However, the FX spec does not specify what metadata can or will be there. Export IR provides a stronger contract, specifically all `call_function` nodes will guarantee having and only having the following metadata fields:
L560:   * `node.meta["stack_trace"]` is a string containing the Python stack trace referencing the original Python source code. An example stack trace looks like:
L561: 
L562:     File "my_module.py", line 19, in forward
L563:     return x + dummy_helper(y)
L564:     File "helper_utility.py", line 89, in dummy_helper
L565:     return y + 1
L566: 
L567: 
L568:   * `node.meta["val"]` describes the output of running the operation. It can be of type `<symint>`, `<FakeTensor>`, a `List[Union[FakeTensor, SymInt]]`, or `None`.
L569:   * `node.meta["nn_module_stack"]` describes the “stacktrace” of the cite244†`torch.nn.Module` from which the node came, if it was from a cite244†`torch.nn.Module` call. For example, if a node containing the `addmm` op called from a cite251†`torch.nn.Linear` module inside of a cite252†`torch.nn.Sequential` module, the `nn_module_stack` would look something like:
L570: 
L571:     {'self_linear': ('self.linear', <class 'torch.nn.Linear'>), 'self_sequential': ('self.sequential', <class 'torch.nn.Sequential'>)}
L572:   * `node.meta["source_fn_stack"]` contains the torch function or the leaf cite244†`torch.nn.Module` class this node was called from before decomposition. For example, a node containing the `addmm` op from a cite251†`torch.nn.Linear` module call would contain cite251†`torch.nn.Linear` in their `source_fn`, and a node containing the `addmm` op from a `torch.nn.functional.Linear` module call would contain `torch.nn.functional.Linear` in their `source_fn`.
L573: ### placeholdercite253†#
L574: 
L575: Placeholder represents an input to a graph. Its semantics are exactly the same as in FX. Placeholder nodes must be the first N nodes in the nodes list of a graph. N can be zero.
L576: 
L577: Representation in FX
L578: 
L579:     %name = placeholder[target = name](args = ())
L580: 
L581: 
L582: The target field is a string which is the name of input.
L583: 
L584: `args`, if non-empty, should be of size 1 representing the default value of this input.
L585: 
L586: Metadata
L587: Placeholder nodes also have `meta[‘val’]`, like `call_function` nodes. The `val` field in this case represents the input shape/dtype that the graph is expected to receive for this input parameter.
L588: ### outputcite254†#
L589: 
L590: An output call represents a return statement in a function; it thus terminates the current graph. There is one and only one output node, and it will always be the last node of the graph.
L591: 
L592: Representation in FX
L593: 
L594:     output[](args = (%something, …))
L595: 
L596: 
L597: This has the exact semantics as in cite239†`torch.fx` . `args` represents the node to be returned.
L598: 
L599: Metadata
L600: 
L601: Output node has the same metadata as `call_function` nodes.
L602: ### get_attrcite255†#
L603: 
L604: `get_attr` nodes represent reading a submodule from the encapsulating cite245†`torch.fx.GraphModule` . Unlike a vanilla FX graph from cite256†`torch.fx.symbolic_trace()` in which `get_attr` nodes are used to read attributes such as parameters and buffers from the top-level cite245†`torch.fx.GraphModule` , parameters and buffers are passed in as inputs to the graph module, and stored in the top-level cite243†`torch.export.ExportedProgram` .
L605: Representation in FX
L606: 
L607:     %name = get_attr[target = name](args = ())
L608: 
L609: 
L610: Example
L611: 
L612: Consider the following model:
L613: 
L614:     from functorch.experimental.control_flow import cond
L615: 
L616:     def true_fn(x):
L617:         return x.sin()
L618: 
L619:     def false_fn(x):
L620:         return x.cos()
L621: 
L622:     def f(x, y):
L623:         return cond(y, true_fn, false_fn, [x])
L624: Graph:
L625: 
L626:     graph():
L627:         %x_1 : [num_users=1] = placeholder[target=x_1]
L628:         %y_1 : [num_users=1] = placeholder[target=y_1]
L629:         %true_graph_0 : [num_users=1] = get_attr[target=true_graph_0]
L630:         %false_graph_0 : [num_users=1] = get_attr[target=false_graph_0]
L631:         %conditional : [num_users=1] = call_function[target=torch.ops.higher_order.cond](args = (%y_1, %true_graph_0, %false_graph_0, [%x_1]), kwargs = {})
L632:         return conditional
L633: The line, `%true_graph_0 : [num_users=1] = get_attr[target=true_graph_0]`, reads the submodule `true_graph_0` which contains the `sin` operator.
L634: ## Referencescite257†#
L635: 
L636: ### SymIntcite258†#
L637: 
L638: A SymInt is an object that can either be a literal integer or a symbol that represents an Integer (represented in Python by `sympy.Symbol` class). When SymInt is a symbol, it describes a variable of type integer that is unknown to the graph at compile time, that is, its value is only known at runtime.
L639: ### FakeTensorcite259†#
L640: 
L641: A FakeTensor is an object that contains the metadata of a tensor. It can be viewed as having the following metadata.
L642: 
L643:     class FakeTensor:
L644:       size: List[SymInt]
L645:       dtype: torch.dtype
L646:       device: torch.device
L647:       dim_order: List[int]  # This doesn't exist yet
L648: The size field of FakeTensor is a list of integers or SymInts. If SymInts are present, this means this tensor has a dynamic shape. If integers are present, it is assumed that the tensor will have that exact static shape. The rank of the TensorMeta is never dynamic. The dtype field represents the dtype of the output of that node. There are no implicit type promotions in Edge IR. There are no strides in FakeTensor.
L649: 
L650: In other words:
L651:   * If the operator in node.target returns a Tensor, then `node.meta['val']` is a FakeTensor describing that tensor.
L652: 
L653:   * If the operator in node.target returns an n-tuple of Tensors, then `node.meta['val']` is an n-tuple of FakeTensors describing each tensor.
L654: 
L655:   * If the operator in node.target returns an int/float/scalar that is known at compile time, then `node.meta['val']` is None.
L656:   * If the operator in node.target returns an int/float/scalar that is not known at compile time, then `node.meta['val']` is of type SymInt.
L657: 
L658: For example:
L659: 
L660:   * `aten::add` returns a Tensor; so its spec will be a FakeTensor with dtype and size of the tensor returned by this operator.
L661: 
L662:   * `aten::sym_size` returns an integer; so its val will be a SymInt because its value is only available at runtime.
L663:   * `max_pool2d_with_indexes` returns a tuple of (Tensor, Tensor); so the spec will also be a 2-tuple of FakeTensor objects, the first TensorMeta describes the first element of the return value etc.
L664: 
L665: Python code:
L666: 
L667:     def add_one(x):
L668:       return torch.ops.aten(x, 1)
L669: 
L670: 
L671: Graph:
L672: 
L673:     graph():
L674:       %ph_0 : [#users=1] = placeholder[target=ph_0]
L675:       %add_tensor : [#users=1] = call_function[target=torch.ops.aten.add.Tensor](args = (%ph_0, 1), kwargs = {})
L676:       return [add_tensor]
L677: FakeTensor:
L678: 
L679:     FakeTensor(dtype=torch.int, size=[2,], device=CPU)
L680: ### Pytree-able Typescite260†#
L681: 
L682: We define a type “Pytree-able”, if it is either a leaf type or a container type that contains other Pytree-able types.
L683: 
L684: Note:
L685:
