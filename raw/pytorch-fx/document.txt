L3730: # torch.fxcite3325†#
L3731: 
L3732: Created On: Dec 15, 2020 | Last Updated On: May 08, 2026
L3733: ## Overviewcite3326†#
L3734: FX is a toolkit for developers to use to transform `nn.Module` instances. FX consists of three main components: a symbolic tracer, an intermediate representation, and Python code generation. A demonstration of these components in action:
L3735: 
L3736:     import torch
L3737: 
L3738: 
L3739:     # Simple module for demonstration
L3740:     class MyModule(torch.nn.Module):
L3741:         def __init__(self) -> None:
L3742:             super().__init__()
L3743:             self.param = torch.nn.Parameter(torch.rand(3, 4))
L3744:             self.linear = torch.nn.Linear(4, 5)
L3745: 
L3746:         def forward(self, x):
L3747:             return self.linear(x + self.param).clamp(min=0.0, max=1.0)
L3748: 
L3749: 
L3750:     module = MyModule()
L3751: 
L3752:     from torch.fx import symbolic_trace
L3753: 
L3754:     # Symbolic tracing frontend - captures the semantics of the module
L3755:     symbolic_traced: torch.fx.GraphModule = symbolic_trace(module)
L3756: 
L3757:     # High-level intermediate representation (IR) - Graph representation
L3758:     print(symbolic_traced.graph)
L3759:     """
L3760:     graph():
L3761:         %x : [num_users=1] = placeholder[target=x]
L3762:         %param : [num_users=1] = get_attr[target=param]
L3763:         %add : [num_users=1] = call_function[target=operator.add](args = (%x, %param), kwargs = {})
L3764:         %linear : [num_users=1] = call_module[target=linear](args = (%add,), kwargs = {})
L3765:         %clamp : [num_users=1] = call_method[target=clamp](args = (%linear,), kwargs = {min: 0.0, max: 1.0})
L3766:         return clamp
L3767:     """
L3768: 
L3769:     # Code generation - valid Python code
L3770:     print(symbolic_traced.code)
L3771:     """
L3772:     def forward(self, x):
L3773:         param = self.param
L3774:         add = x + param;  x = param = None
L3775:         linear = self.linear(add);  add = None
L3776:         clamp = linear.clamp(min = 0.0, max = 1.0);  linear = None
L3777:         return clamp
L3778:     """
L3779: The symbolic tracer performs “symbolic execution” of the Python code. It feeds fake values, called Proxies, through the code. Operations on these Proxies are recorded. More information about symbolic tracing can be found in the cite3327†`symbolic_trace()` and cite3328†`Tracer` documentation.
L3780: The intermediate representation is the container for the operations that were recorded during symbolic tracing. It consists of a list of Nodes that represent function inputs, callsites (to functions, methods, or cite3329†`torch.nn.Module` instances), and return values. More information about the IR can be found in the documentation for cite3330†`Graph` . The IR is the format on which transformations are applied.
L3781: Python code generation is what makes FX a Python-to-Python (or Module-to-Module) transformation toolkit. For each Graph IR, we can create valid Python code matching the Graph’s semantics. This functionality is wrapped up in cite3331†`GraphModule` , which is a cite3329†`torch.nn.Module` instance that holds a cite3330†`Graph` as well as a `forward` method generated from the Graph.
L3782: Taken together, this pipeline of components (symbolic tracing -> intermediate representation -> transforms -> Python code generation) constitutes the Python-to-Python transformation pipeline of FX. In addition, these components can be used separately. For example, symbolic tracing can be used in isolation to capture a form of the code for analysis (and not transformation) purposes. Code generation can be used for programmatically generating models, for example from a config file.
L3783: There are many uses for FX!
L3784: Several example transformations can be found at the cite3332†examples†github.com repository.
L3785: ## Writing Transformationscite3333†#
L3786: What is an FX transform? Essentially, it’s a function that looks like this.
L3787: 
L3788: 
L3789:     import torch
L3790:     import torch.fx
L3791: 
L3792:     def transform(m: nn.Module,
L3793:                     tracer_class : type = torch.fx.Tracer) -> torch.nn.Module:
L3794:         # Step 1: Acquire a Graph representing the code in `m`
L3795: 
L3796:         # NOTE: torch.fx.symbolic_trace is a wrapper around a call to
L3797:         # fx.Tracer.trace and constructing a GraphModule. We'll
L3798:         # split that out in our transform to allow the caller to
L3799:         # customize tracing behavior.
L3800:         graph : torch.fx.Graph = tracer_class().trace(m)
L3801: 
L3802:         # Step 2: Modify this Graph or create a new one
L3803:         graph = ...
L3804: 
L3805:         # Step 3: Construct a Module to return
L3806:         return torch.fx.GraphModule(m, graph)
L3807: Your transform will take in a cite3329†`torch.nn.Module` , acquire a cite3330†`Graph` from it, do some modifications, and return a new cite3329†`torch.nn.Module` . You should think of the cite3329†`torch.nn.Module` that your FX transform returns as identical to a regular cite3329†`torch.nn.Module` – you can pass it to another FX transform, or you can run it. Ensuring that the inputs and outputs of your FX transform are a cite3329†`torch.nn.Module` will allow for composability.
L3808: 
L3809: Note
L3810: It is also possible to modify an existing cite3331†`GraphModule` instead of creating a new one, like so:
L3811: 
L3812:     import torch
L3813:     import torch.fx
L3814: 
L3815:     def transform(m : nn.Module) -> nn.Module:
L3816:         gm : torch.fx.GraphModule = torch.fx.symbolic_trace(m)
L3817: 
L3818:         # Modify gm.graph
L3819:         # <...>
L3820: 
L3821:         # Recompile the forward() method of `gm` from its Graph
L3822:         gm.recompile()
L3823: 
L3824:         return gm
L3825: Note that you MUST call cite3334†`GraphModule.recompile()` to bring the generated `forward()` method on the `GraphModule` in sync with the modified cite3330†`Graph` .
L3826: 
L3827: Given that you’ve passed in a cite3329†`torch.nn.Module` that has been traced into a cite3330†`Graph` , there are now two primary approaches you can take to building a new cite3330†`Graph` .
L3828: ### A Quick Primer on Graphscite3335†#
L3829: 
L3830: Full treatment of the semantics of graphs can be found in the cite3330†`Graph` documentation, but we are going to cover the basics here. A cite3330†`Graph` is a data structure that represents a method on a cite3331†`GraphModule` . The information that this requires is:
L3831: 
L3832:   * What are the inputs to the method?
L3833: 
L3834:   * What are the operations that run inside the method?
L3835: 
L3836:   * What is the output (i.e. return) value from the method?
L3837: All three of these concepts are represented with cite3336†`Node` instances. Let’s see what we mean by that with a short example:
L3838: 
L3839: 
L3840:     import torch
L3841:     import torch.fx
L3842: 
L3843:     class MyModule(torch.nn.Module):
L3844:         def __init__(self):
L3845:             super().__init__()
L3846:             self.param = torch.nn.Parameter(torch.rand(3, 4))
L3847:             self.linear = torch.nn.Linear(4, 5)
L3848: 
L3849:         def forward(self, x):
L3850:             return torch.topk(torch.sum(
L3851:                 self.linear(x + self.linear.weight).relu(), dim=-1), 3)
L3852: 
L3853:     m = MyModule()
L3854:     gm = torch.fx.symbolic_trace(m)
L3855: 
L3856:     gm.graph.print_tabular()
L3857: Here we define a module `MyModule` for demonstration purposes, instantiate it, symbolically trace it, then call the cite3337†`Graph.print_tabular()` method to print out a table showing the nodes of this cite3330†`Graph` :
L3858: opcode  | name  | target  | args  | kwargs
L3859: --- | --- | --- | --- | ---
L3860: placeholder  | x  | x  | ()  | {}
L3861: get_attr  | linear_weight  | linear.weight  | ()  | {}
L3862: call_function  | add_1  |  | (x, linear_weight)  | {}
L3863: call_module  | linear_1  | linear  | (add_1,)  | {}
L3864: call_method  | relu_1  | relu  | (linear_1,)  | {}
L3865: call_function  | sum_1  | <built-in method sum …>  | (relu_1,)  | {‘dim’: -1}
L3866: call_function  | topk_1  | <built-in method topk …>  | (sum_1, 3)  | {}
L3937: Another way of manipulating cite3330†`Graph` \s is by reusing the cite3352†`Proxy` machinery used in symbolic tracing. For example, let’s imagine that we wanted to write a transformation that decomposed PyTorch functions into smaller operations. It would transform every `F.relu(x)` call into `(x > 0) * x`. One possibility would be to perform the requisite graph rewriting to insert the comparison and multiplication after the `F.relu`, and then clean up the original `F.relu`.
L3938: However, we can automate this process by using cite3352†`Proxy` objects to automatically record operations into the cite3330†`Graph` .
L3939: To use this method, we write the operations that we want inserted as regular PyTorch code and invoke that code with cite3352†`Proxy` objects as arguments. These cite3352†`Proxy` objects will capture the operations that are performed on them and append them to the cite3330†`Graph` .
L3940: 
L3941: 
L3942:     # Note that this decomposition rule can be read as regular Python
L3943:     def relu_decomposition(x):
L3944:         return (x > 0) * x
L3945: 
L3946:     decomposition_rules = {}
L3947:     decomposition_rules[F.relu] = relu_decomposition
L3948:     def decompose(model: torch.nn.Module,
L3949:                     tracer_class : type = fx.Tracer) -> torch.nn.Module:
L3950:         """
L3951:         Decompose `model` into smaller constituent operations.
L3952:         Currently,this only supports decomposing ReLU into its
L3953:         mathematical definition: (x > 0) * x
L3954:         """
L3955:         graph : fx.Graph = tracer_class().trace(model)
L3956:         new_graph = fx.Graph()
L3957:         env = {}
L3958:         tracer = torch.fx.proxy.GraphAppendingTracer(new_graph)
L3959:         for node in graph.nodes:
L3960:             if node.op == 'call_function' and node.target in decomposition_rules:
L3961:                 # By wrapping the arguments with proxies,
L3962:                 # we can dispatch to the appropriate
L3963:                 # decomposition rule and implicitly add it
L3964:                 # to the Graph by symbolically tracing it.
L3965:                 proxy_args = [
L3966:                     fx.Proxy(env[x.name], tracer) if isinstance(x, fx.Node) else x for x in node.args]
L3967:                 output_proxy = decomposition_rules[node.target](*proxy_args)
L3968: 
L3969:                 # Operations on `Proxy` always yield new `Proxy`s, and the
L3970:                 # return value of our decomposition rule is no exception.
L3971:                 # We need to extract the underlying `Node` from the `Proxy`
L3972:                 # to use it in subsequent iterations of this transform.
L3973:                 new_node = output_proxy.node
L3974:                 env[node.name] = new_node
L3975:             else:
L3976:                 # Default case: we don't have a decomposition rule for this
L3977:                 # node, so just copy the node over into the new graph.
L3978:                 new_node = new_graph.node_copy(node, lambda x: env[x.name])
L3979:                 env[node.name] = new_node
L3980:         return fx.GraphModule(model, new_graph)
L3981: In addition to avoiding explicit graph manipulation, using cite3352†`Proxy` \s also allows you to specify your rewrite rules as native Python code. For transformations that require a large amount of rewrite rules (such as vmap or grad), this can often improve readability and maintainability of the rules. Note that while calling cite3352†`Proxy` we also passed a tracer pointing to the underlying variable `graph`. This is done so if in case the operations in graph are n-ary (e.g.
L3982: add is a binary operator) the call to cite3352†`Proxy` does not create multiple instances of a graph tracer which can lead to unexpected runtime errors. We recommend this method of using cite3352†`Proxy` especially when the underlying operators can not be safely assumed to be unary.
L3983: A worked example of using cite3352†`Proxy` \s for cite3330†`Graph` manipulation can be found cite3353†here†github.com .
L3984: ### The Interpreter Patterncite3354†#
L3985: A useful code organizational pattern in FX is to loop over all the cite3336†`Node` \s in a cite3330†`Graph` and execute them. This can be used for several things including runtime analysis of values flowing through the graph or transformation of the code via retracing with cite3352†`Proxy` \s. For example, suppose we want to run a cite3331†`GraphModule` and record the cite3355†`torch.Tensor` shape and dtype properties on the nodes as we see them at runtime. That might look like:
L3986: 
L3987: 
L3988:     import torch
L3989:     import torch.fx
L3990:     from torch.fx.node import Node
L3991: 
L3992:     from typing import Dict
L3993: 
L3994:     class ShapeProp:
L3995:         """
L3996:         Shape propagation. This class takes a `GraphModule`.
L3997:         Then, its `propagate` method executes the `GraphModule`
L3998:         node-by-node with the given arguments. As each operation
L3999:         executes, the ShapeProp class stores away the shape and
L4000:         element type for the output values of each operation on
L4001:         the `shape` and `dtype` attributes of the operation's
L4002:         `Node`.
L4003:         """
L4004:         def __init__(self, mod):
L4005:             self.mod = mod
L4006:             self.graph = mod.graph
L4007:             self.modules = dict(self.mod.named_modules())
L4008: 
L4009:         def propagate(self, *args):
L4010:             args_iter = iter(args)
L4011:             env : Dict[str, Node] = {}
L4012: 
L4013:             def load_arg(a):
L4014:                 return torch.fx.graph.map_arg(a, lambda n: env[n.name])
L4015: 
L4016:             def fetch_attr(target : str):
L4017:                 target_atoms = target.split('.')
L4018:                 attr_itr = self.mod

L4050: In addition to executing operations, we can also generate a new `Graph` by feeding cite3352†`Proxy` values through an interpreter. Similarly, we provide the cite3357†`Transformer` class to encompass this pattern.
L4051: cite3357†`Transformer` behaves similarly to cite3356†`Interpreter` , but instead of calling the `run` method to get a concrete output value from the Module, you would call the cite3358†`Transformer.transform()` method to return a new cite3331†`GraphModule` which was subject to any transformation rules you installed as overridden methods.

L4058: ## Debuggingcite3362†#
L4059: ### Introductioncite3363†#
L4060: 
L4061: Often in the course of authoring transformations, our code will not be quite right. In this case, we may need to do some debugging. The key is to work backwards: first, check the results of invoking the generated module to prove or disprove correctness. Then, inspect and debug the generated code. Then, debug the process of transformations that led to the generated code.
L4062: 
L4063: If you’re not familiar with debuggers, please see the auxiliary section cite3364†Available Debuggers .
L4064: ### Common Pitfalls in Transform Authoringcite3365†#
L4065:   * Nondeterministic `set` iteration order. In Python, the `set` datatype is unordered. Using `set` to contain collections of objects like `Node`\ s, for example, can cause unexpected nondeterminism. An example is iterating over a set of `Node` s to insert them into a `Graph`. Because the `set` data type is unordered, the ordering of the operations in the output program will be nondeterministic and can change across program invocations.
L4066: The recommended alternative is to use a `dict` data type, which is cite3366†insertion ordered†mail.python.org as of Python 3.7 (and as of cPython 3.6). A `dict` can be used equivalently to a set by storing values to be deduplicated in the keys of the `dict`.
L4067: ### Checking Correctness of Modulescite3367†#
L4068: Because the output of most deep learning modules consists of floating point cite3355†`torch.Tensor` instances, checking for equivalence between the results of two cite3329†`torch.nn.Module` is not as straightforward as doing a simple equality check.
